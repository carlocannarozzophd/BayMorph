# BayMorph API Policy

This document defines the interfaces that BayMorph users and contributors may rely on. It is a policy and navigation guide, not an autogenerated symbol reference.

## API philosophy

BayMorph separates user-facing workflow orchestration from reusable scientific components and internal implementation details. The public contract is intentionally smaller than the set of importable Python objects.

Users should prefer the highest-level interface that satisfies their needs:

1. the command-line interface and `BayMorphRunner` for complete, configuration-driven workflows;
2. documented top-level objects for direct scientific use;
3. documented subpackage interfaces for advanced composition and extension;
4. internal modules only when developing BayMorph itself.

Importability alone does not make an interface stable. Stability is determined by the categories below and by explicit documentation.

## Stable Public API

The Stable Public API is the recommended interface for normal scientific use. Compatible changes may extend it, but existing supported behavior will not be removed or changed incompatibly without deprecation.

### Command-line interface

The installed `baymorph` command is public. Its documented commands and options are part of the compatibility contract.

The primary entry points are:

```bash
baymorph init PROJECT_DIRECTORY
baymorph examples DESTINATION
```

Additional documented CLI workflows are public when described in the project documentation or command help.

### High-level Python interface

The principal Python entry point is:

```python
from baymorph import BayMorphRunner
```

`BayMorphRunner` is the supported orchestration layer for configuration-driven image preparation, PSF construction, fitting, and result loading.

The following core data abstractions are also stable public interfaces:

```python
from baymorph import (
    ImageData,
    Observation,
    ObservationMetadata,
    PosteriorResult,
    RealFitProducts,
)
```

The supported morphology models are public:

```python
from baymorph import DoubleSersicModel, SersicModel
```

The configuration and top-level workflow functions documented in the README, official notebooks, and examples are public when imported from `baymorph`.

### Public import rule

For stable usage, prefer imports from the package root:

```python
from baymorph import BayMorphRunner, Observation, SersicModel
```

Top-level names listed in `baymorph.__all__` are intentionally exposed. However, specialized utilities may belong to the Advanced API even when re-exported for convenience. Their behavioral stability is governed by their documentation and category in this file.

## Advanced API

The Advanced API supports researchers who need to compose lower-level workflows, replace individual stages, or inspect intermediate products. These interfaces are supported and tested, but may evolve more quickly than the Stable Public API as scientific workflows mature.

Advanced interfaces include documented objects and functions from:

- `baymorph.analysis`
- `baymorph.core`
- `baymorph.fitting`
- `baymorph.likelihood`
- `baymorph.pipeline`
- `baymorph.plotting`
- `baymorph.results`
- `baymorph.simulation`
- `baymorph.stats`

Typical advanced use cases include:

- constructing or validating `Observation` objects directly;
- invoking image-preparation stages independently;
- selecting or building empirical PSFs;
- configuring fitters and parameter sets;
- rendering model components;
- computing posterior summaries and radial-profile diagnostics;
- loading or saving intermediate workflow products.

Advanced users should import from the owning subpackage when ownership matters:

```python
from baymorph.pipeline import prepare_real_image_from_config
from baymorph.fitting import DynestyFitter, ParameterSet
```

Minor releases may add parameters, return metadata, or reorganize advanced helpers. Incompatible changes still require release notes and, whenever practical, a deprecation period.

## Internal API

Anything not documented as Stable Public or Advanced is internal. Internal interfaces include:

- modules or names beginning with `_`;
- implementation helpers not included in public documentation;
- test utilities;
- private serialization details;
- undocumented module-level constants;
- intermediate structures used only inside one pipeline stage.

Internal interfaces may change without deprecation, including in patch releases when required to fix defects. External code should not depend on them.

Importing an internal object is permitted for experimentation, but it transfers compatibility responsibility to the caller.

## Backward compatibility

BayMorph follows semantic versioning in spirit:

- patch releases fix defects and may improve internal implementation without changing supported behavior;
- minor releases add compatible functionality and may deprecate older interfaces;
- major releases may remove deprecated interfaces or introduce other incompatible changes.

For the Stable Public API, backward compatibility covers:

- documented import paths;
- required positional and keyword arguments;
- documented return types and meanings;
- configuration keys described as supported;
- serialized products explicitly documented as reusable across versions;
- documented CLI commands, arguments, and exit behavior.

Compatibility does not guarantee byte-for-byte identical numerical output. Changes that improve scientific correctness, dependency behavior, or numerical robustness may alter results. Such changes must be documented and validated.

Private implementation details, incidental exception messages, plotting aesthetics, and undocumented dictionary ordering are not compatibility guarantees.

## Deprecation policy

When a supported interface must change, BayMorph will normally:

1. introduce the replacement;
2. retain the old interface temporarily;
3. emit a `DeprecationWarning` or an equivalent clear runtime warning where practical;
4. document the migration in `CHANGELOG.md`;
5. remove the deprecated interface only after an appropriate transition period.

The normal minimum transition period is one minor release. Longer periods may be used for widely adopted interfaces or configuration formats.

A deprecation notice should state:

- what is deprecated;
- why it is changing;
- the supported replacement;
- the earliest version in which removal may occur.

Immediate removal is reserved for security issues, scientifically invalid behavior, interfaces that were never documented as supported, or cases where retaining the old behavior is technically impossible. Such exceptions must be explained in the changelog.

## Adding a public interface

New public interfaces should:

- have a clear architectural owner;
- include type hints and a complete docstring;
- be covered by tests;
- be exported deliberately rather than incidentally;
- appear in user documentation or an official example;
- avoid exposing backend-specific details unless those details are part of the intended contract.

Contributors proposing a new stable interface should explain why the Advanced API is insufficient and describe the intended compatibility commitment in the pull request.
