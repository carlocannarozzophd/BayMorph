# BayMorph API Policy

This document defines the supported programming interfaces of BayMorph.

It is a policy document rather than an autogenerated API reference. Its purpose is to define which interfaces users may safely rely upon and how compatibility is maintained across releases.

---

# API Philosophy

BayMorph deliberately separates:

* user-facing workflow orchestration;
* reusable scientific components;
* internal implementation details.

The public API is intentionally smaller than the set of importable Python objects.

Users should prefer the highest-level interface that satisfies their needs:

1. the command-line interface and `BayMorphRunner`;
2. documented top-level Python objects;
3. documented advanced subpackage interfaces;
4. internal modules only when developing BayMorph itself.

Importability alone does **not** imply API stability.

Only interfaces documented in this policy are covered by BayMorph's compatibility guarantees.

---

# Stable Public API

The Stable Public API is recommended for normal scientific use.

Compatible releases may extend this interface, but existing documented behavior will not change incompatibly without deprecation.

## Command-Line Interface

The installed `baymorph` command is part of the stable public API.

Current supported commands include:

```bash
baymorph init PROJECT_DIRECTORY
baymorph examples DESTINATION
```

Additional commands become part of the public API once documented in the official documentation or command help.

---

## High-Level Python Interface

The preferred Python entry point is:

```python
from baymorph import BayMorphRunner
```

`BayMorphRunner` is the supported orchestration layer for configuration-driven workflows.

Stable public data abstractions include:

```python
from baymorph import (
    ImageData,
    Observation,
    ObservationMetadata,
    PosteriorResult,
    RealFitProducts,
)
```

Supported morphology models include:

```python
from baymorph import (
    SersicModel,
    DoubleSersicModel,
)
```

Configuration loading and workflow helpers documented in the README, official notebooks, or examples are also considered part of the Stable Public API when imported from the package root.

---

## Public Import Rule

Whenever possible, import directly from the top-level package:

```python
from baymorph import (
    BayMorphRunner,
    Observation,
    SersicModel,
)
```

Names intentionally exported through `baymorph.__all__` are public.

Some advanced utilities may also be re-exported for convenience. Their compatibility guarantees are determined by their category in this document rather than by their import path.

---

# Advanced API

The Advanced API supports users who wish to compose lower-level workflows or customize individual pipeline stages.

These interfaces are supported and tested but may evolve more rapidly than the Stable Public API.

Advanced interfaces include documented objects from:

* `baymorph.analysis`
* `baymorph.core`
* `baymorph.fitting`
* `baymorph.likelihood`
* `baymorph.pipeline`
* `baymorph.plotting`
* `baymorph.results`
* `baymorph.simulation`
* `baymorph.stats`

Typical advanced use cases include:

* constructing `Observation` objects;
* executing image-preparation stages independently;
* building empirical PSFs;
* configuring fitters;
* rendering model components;
* computing posterior diagnostics;
* loading or saving intermediate workflow products.

When ownership matters, import directly from the responsible subpackage.

Example:

```python
from baymorph.pipeline import (
    prepare_real_image_from_config,
)

from baymorph.fitting import (
    DynestyFitter,
    ParameterSet,
)
```

Minor releases may extend these interfaces or add metadata without affecting the Stable Public API.

---

# Internal API

Everything not documented as Stable Public or Advanced is considered internal.

Examples include:

* names beginning with `_`;
* implementation helpers;
* internal pipeline utilities;
* test utilities;
* private serialization details;
* undocumented constants.

Internal interfaces may change without notice.

Importing them is allowed for experimentation but transfers compatibility responsibility entirely to the caller.

---

# Backward Compatibility

BayMorph follows Semantic Versioning in spirit.

* Patch releases fix defects and improve implementation without changing supported behavior.
* Minor releases add compatible functionality and may deprecate older interfaces.
* Major releases may remove deprecated interfaces or introduce incompatible changes.

For the Stable Public API, compatibility includes:

* documented import paths;
* documented function signatures;
* documented return types;
* supported configuration keys;
* reusable serialized products explicitly documented as stable;
* documented CLI commands and behavior.

Scientific improvements may legitimately change numerical results when they improve correctness, robustness, or statistical validity.

Such changes will always be documented.

---

# Deprecation Policy

Supported interfaces normally follow this lifecycle:

1. introduce the replacement;
2. retain the existing interface temporarily;
3. emit a clear deprecation warning whenever practical;
4. document the migration in `CHANGELOG.md`;
5. remove the deprecated interface only after an appropriate transition period.

The normal minimum transition period is one minor release.

Each deprecation should clearly state:

* what is deprecated;
* why it is changing;
* the recommended replacement;
* the earliest planned removal version.

Immediate removal is reserved for security issues, scientifically invalid behavior, undocumented interfaces, or situations where compatibility cannot reasonably be preserved.

---

# Adding New Public Interfaces

New Stable Public APIs should:

* have a clearly defined architectural owner;
* include complete type hints;
* include comprehensive docstrings;
* be covered by automated tests;
* be exported intentionally;
* appear in the official documentation or tutorial notebooks;
* avoid exposing backend-specific implementation details unless those details are explicitly part of the intended contract.

Contributors proposing a new public interface should explain why the existing Advanced API is insufficient and describe the desired long-term compatibility commitment.

---

# Guiding Principle

BayMorph favors a small, stable, and well-documented public interface.

Internal implementation is expected to evolve as the scientific capabilities of the project grow, while user-facing workflows should remain predictable, reproducible, and straightforward across releases.
